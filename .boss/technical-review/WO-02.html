1. Task overview and change impact

1.1 Scope and distribution

13 tasks; two implementation tracks (playback and account), followed by independent review and QA. Section 2 enumerates every write set, normally no more than five files per task. One new registration-result source file is proposed. New permanent regression cases are added to existing test files. No parallel player or state-management system is introduced.

1.2 Behavioral decisions

  1. The sleep timer belongs to the current listening session. Station→episode→episode/station keeps the same visible deadline, without restarting its duration. Pause/retry preserves it. Local stop, remote idle and disposal cancel it. A timer from a finished session cannot stop a later session.
  2. Preserve completion internally without requiring a new public enum across all Widgets. Replay serializes seek(0) with loads and checks episode ID and generation before and after await. Source replacement, pause, stop and disposal invalidate old replay work. Seeking alone never requests playback.
  3. If rewind fails, reload only the same episode while the user's request remains current; otherwise cancel. End in playing or the existing actionable failure state, never indefinite loading. Retain the Android foreground check before starting audio.
  4. Proposed NEW type AccountRegistrationResult, in the planned file below, represents successful account creation and normalized verification-delivery outcome. It carries no email, code or raw exception. Account-creation failure remains the existing account exception, not a partial-success result.
  5. Delivery outcomes sent, deliveryFailed, rateLimited are proposed names to finalize in implementation. Do not infer sent from an Auth user existing. Keep the controller's public Future<void> register for its screen callers; consume the new result internally. Starting/failing a subsequent resend clears stale sent state so success and failure cannot coexist.
  6. Existing AR/EN resources verificationDeliveryFailed, verificationRateLimited, verificationCodeSent, resendVerificationCode in lib/l10n/app_ar.arb and app_en.arb are sufficient. No ARB changes planned. If new copy becomes necessary, declare ownership of both ARBs and generated outputs and add flutter gen-l10n before expanding the write set; never hard-code UI text.

1.3 Boundaries and shared files

  • lib/app/providers.dart and station_content source/screens are read-only in this package. No DI, discovery or navigation change is expected. Writing them would conflict with WO-03 and requires explicit reassignment and serialization before implementation.
  • No automatic resend loop, duplicate account creation or local verified privilege after account creation/email dispatch.
  • Registration interface changes are split to keep task write sets small. T06–T09 form one integration unit; do not merge an intermediate commit with broken implementers. Compilation failures are not behavioral RED evidence.
  • No dependency/lock/build/deployment-file edits, installation or irreversible operations are planned. The current task is planning only; implementation follows the user's authorization and the master plan's approval boundary.
